# Проект домашней сети и VPN

## Назначение

Этот проект используется для диагностики и аккуратной настройки домашней сети Игоря: Keenetic, XKeen/Xray, VLESS Reality, Wi-Fi, маршрутизация отдельных сервисов и клиентские устройства. Основная задача — установить фактическую причину сбоя и только затем применять минимальное обратимое изменение.

В каталоге могут находиться локальные вспомогательные приложения и Chrome-launcher-файлы. Их наличие не меняет основное назначение проекта и не разрешает редактировать их без отдельной задачи.

## Известная топология

- Роутер обычно доступен по `192.168.1.1` через SSH как `root`. Доступность и адрес проверять заново.
- На роутере используется XKeen с Xray; ожидаемый рабочий режим — `Hybrid`.
- Активный routing-файл: `/opt/etc/xray/configs/05_routing.json`.
- Логи Xray:
  - `/opt/var/log/xray/access.log`
  - `/opt/var/log/xray/error.log`
- Основные outbound-теги: `direct` и `vless-reality`. Остальные теги и их параметры проверять по текущему конфигу.
- Домашние Wi-Fi-сети исторически назывались `Kotenokanala24` и `Kotenokanala 5`.
- Для 5 ГГц ранее был подтверждён канал 36 с шириной 40 МГц вместо DFS 56/80 МГц. Перед выводами проверять текущую конфигурацию.

## Корпоративные VPN и браузеры

- Внутренний сервис может идти внутри Cisco/Continent через `utun`, а домашний Xray видеть только внешний endpoint корпоративного VPN. Всегда проверять два слоя: Mac DNS/route/interface до внутреннего IP и Keenetic/Xray-маршрут внешнего туннеля.
- Cisco и Continent не взаимозаменяемы: проверять маршрут отдельно для каждого hostname. Частично отрисованная или закэшированная оболочка не доказывает доступность API, WebSocket, превью и данных.
- Глобальный блок/разрешение UDP/443 влияет не только на корпоративный DTLS, но и на QUIC других сервисов. Предпочитать узкое исключение для подтверждённого текущего endpoint; после изменения перепроверять затронутый сервис и отсутствие побочного изменения маршрутов YouTube/KinoPub.
- Разделять ошибки браузера: `NXDOMAIN` — DNS/VPN; HSTS/недоверенный корпоративный CA — trust chain; HTTP `500` после OAuth-кода — сервер/SSO; skeleton/чёрные превью — зависимые API/CDN/WebSocket. Не называть их VLESS-сбоем без route evidence.
- Не обходить HSTS и не отключать TLS-проверку глобально. Не копировать cookies/SSO-сессии между профилями. Изолированные рабочие Chrome-профили и точечные сертификатные исключения менять только по отдельной задаче.
- Если интерфейс показывает несинхронизированные локальные изменения, не перезагружать вкладку, не закрывать приложение и не чистить site data до сохранения результата или явного разрешения пользователя.

## Известные устройства

- LG webOS / KinoPub: MAC `24:e8:53:33:7f:7e`, исторически часто IP `192.168.1.55`.
- IP-адреса и private MAC мобильных устройств нестабильны. Никогда не фильтровать логи по старому IP без свежих DHCP/ARP/association данных.
- Исторические MAC/IP — только подсказки для поиска, не подтверждение текущего состояния.
- Запрос «посмотри телефон / у жены не работает сервис» по умолчанию означает сетевую диагностику через Keenetic: найти актуальное устройство в DHCP/association/ARP и сопоставить его трафик. Не требовать USB-подключения и не запускать Computer Use, если пользователь явно не просит осмотреть экран телефона.
- Отсутствие телефона среди Mac-приложений или USB-устройств не блокирует сетевую диагностику. Скриншот или доступ к UI запрашивать только для симптома, который нельзя установить по сети.

## Исторические решения, требующие live-проверки

- Для `domain:cdntogo.net` применялось приоритетное правило `direct`; оно помогало в контролируемом KinoPub A/B-тесте, но не доказывает исправность каждого будущего потока.
- Отдельные доменные семьи направлялись через `vless-reality`. Не переносить и не расширять такие правила без свежих логов и проверки зависимых хостов.
- HTTP 200, успешный TLS или открытая CDN-сессия не равны работающему приложению: проверять завершение страницы, рост счётчиков трафика или фактическое воспроизведение.
- `XTLS rejected UDP/443 traffic` может означать ожидаемый отказ QUIC с переходом на TCP; сначала связать запись с конкретным клиентом и сервисом.

## Обязательный порядок диагностики

1. Уточнить затронутое устройство, сервис, симптом и критерий «работает».
2. Начать read-only: получить свежие DHCP, ARP, Wi-Fi association, DNS, ping и статус XKeen.
3. Проверить фактический пользовательский путь: приложение/браузер, основной хост, зависимые хосты, CDN/API и конечный результат.
4. Сопоставить трафик с текущим MAC/IP клиента и свежими Xray-логами.
5. Разделить возможные причины: клиент, Wi-Fi, DNS, direct/VLESS-маршрут, upstream/API, CDN/player, Cloudflare/IP policy.
6. Использовать A/B-тесты по одной переменной: Wi-Fi/мобильная сеть, приложение/браузер, direct/VLESS. Не менять общий роутинг по одному косвенному признаку.
7. Если изменение действительно нужно: backup → минимальное правило → полная валидация → restart → свежие логи → end-to-end проверка → rollback без измеримого улучшения.
8. Фразы «чекни», «посмотри», «потрекай» разрешают самостоятельные read-only проверки в пределах проекта; они не разрешают изменение конфигурации или рестарт.
9. Проверять один и тот же проблемный объект на контролируемых путях. Успешный маленький файл, API или TCP-handshake не опровергает DC-, CDN-, файла- или сессия-специфичный сбой.
10. После временного восстановления или рестарта повторить реальное действие пользователя. Не объявлять исправление только по статусу процесса, синтетическому `curl` или исчезновению строки ошибки.
11. Ошибка DNS/сети из sandbox доказывает только ограничение sandbox. Повторить проверку через разрешённый host/router path до вывода о сервисе.

## Безопасные команды и проверка

```bash
ndmc -c 'show ip dhcp bindings'
ndmc -c 'show associations'
ip neigh show
xkeen -status
```

Перед рестартом проверить весь Xray-конфиг:

```bash
XRAY_LOCATION_ASSET=/opt/etc/xray/dat xray convert pb \
  -outpbfile /tmp/check.pb /opt/etc/xray/configs/*.json
```

Допустим также `xray run -test -confdir <dir>`. На установленной версии не использовать `xray convert pb -c file`: JSON-файлы передаются позиционно. Если обычный SCP требует отсутствующий SFTP subsystem, использовать `scp -O`.

## Правила изменений

- Не менять роутер, Xray, Wi-Fi, DNS или клиентские настройки без доказанной причины и понятного критерия успеха.
- Перед изменением делать датированный backup только затрагиваемого файла.
- Не перезапускать роутер, XKeen, телевизор или приложение во время активной диагностики без необходимости или согласования.
- Не добавлять широкие доменные/IP-правила, если достаточно одного registrable domain или подтверждённой семьи.
- Перед исключением из глобального UDP/443-правила проверить порядок Xray rules, текущий endpoint и возможное влияние на другие сервисы. Не разрешать UDP/443 целиком для устройства как первый тест.
- Предпочитать рестарт только XKeen/Xray, а не всего роутера, когда менялся Xray. Даже после разрешённого рестарта не считать проблему решённой без проверки исходного симптома.
- Не выполнять покупки, авторизации, отправку форм или внешние публикации без отдельного явного разрешения.
- Никогда не сохранять и не выводить в репозиторий VLESS UUID, private/public keys, short IDs, subscription URL, пароли, cookies и токены.
- Публичные шаблоны и старые снимки не считать копией live-конфига.

## Git

- До работы проверять `git status` и сохранять посторонние изменения пользователя.
- Добавлять в коммит только файлы текущей задачи.
- Делать отдельный checkpoint-коммит после завершённого и проверенного этапа.
- Не выполнять `push`, `rebase`, `amend` или переписывание истории без прямой просьбы.

## Формат результата диагностики

Кратко сообщать:

1. Что подтверждено live.
2. Что является исторической подсказкой или гипотезой.
3. Главное узкое место.
4. Что проверено без изменений.
5. Какое минимальное действие предлагается, его риск и rollback.
